### 1. TypeScript 中 type 和 interface 的区别

`type`（类型别名）和 `interface`（接口）都可以描述对象结构，也都支持泛型。

| 对比项 | type | interface |
| --- | --- | --- |
| 表达范围 | 可以表示对象、联合类型、元组、基本类型别名等 | 主要描述对象结构，也能描述函数和索引签名 |
| 同名声明 | 同一作用域内不能重复声明同名类型别名 | 支持声明合并，但同名非函数成员的类型必须一致 |
| 扩展方式 | 通常用交叉类型 `&` 组合 | 使用 `extends` 继承 |
| 属性冲突 | 交叉类型要求同时满足双方约束，不兼容的属性可能变成 `never` | 继承时遇到不兼容的属性通常直接报错 |

```ts
// 两者都能描述对象
type UserType = { name: string };
interface UserInterface {
  name: string;
}

// interface 支持声明合并
interface UserInterface {
  age: number;
}
// UserInterface 现在同时要求 name 和 age

// type 可以直接表达联合类型和元组
type Status = 'loading' | 'success' | 'error';
type Point = [number, number];

// 扩展对象类型
type AdminType = UserType & { role: string };
interface AdminInterface extends UserInterface {
  role: string;
}

// 交叉类型中的属性冲突
type A = { id: string };
type B = { id: number };
type C = A & B; // C['id'] 是 never
```

**面试回答：**两者都能描述对象结构。`interface` 支持声明合并，通过 `extends` 扩展；`type` 的表达范围更广，可以定义联合类型、元组等，通过 `&` 组合类型。描述需要开放扩展的对象契约时可以用 `interface`，表达联合类型或复杂类型运算时可以用 `type`，普通对象类型则按项目约定选择。

参考：[TypeScript 官方文档：Type Aliases 与 Interfaces](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#differences-between-type-aliases-and-interfaces)

### 2. TypeScript 中泛型是什么

泛型就是给类型定义参数，在使用函数、接口、类型别名或类时，再确定具体类型。它可以复用同一套逻辑，同时保留类型检查和类型之间的关联。

例如，一个函数接收什么类型，就返回什么类型：

```ts
function identity<T>(value: T): T {
  return value;
}

const num = identity(123); // 自动推断 T 为 number，返回值为 number
const str = identity<string>('hello'); // 显式指定 T 为 string
```

这里的 `T` 是类型参数，名字可以自定义。参数和返回值使用同一个 `T`，表示它们的类型有关联。如果改用 `any`，就会丢失这种类型信息。

泛型也可以用来描述通用的数据结构：

```ts
interface ApiResponse<T> {
  code: number;
  data: T;
}

interface User {
  name: string;
}

const response: ApiResponse<User> = {
  code: 200,
  data: { name: '小明' },
};
```

如果逻辑依赖某个属性，可以通过 `extends` 约束泛型：

```ts
function getLength<T extends { length: number }>(value: T): number {
  return value.length;
}

getLength('hello'); // 5
getLength([1, 2]); // 2
// getLength(123); // 报错：number 不满足包含 length 属性的约束
```

**面试回答：**泛型是类型参数化，让函数、接口或类在使用时确定具体类型。它能在复用代码的同时保证类型安全，并保留输入、输出等类型之间的关联。比如用 `<T>(value: T) => T` 表达输入和返回值类型一致，也可以通过 `extends` 限制允许传入的类型。

### 3. Nuxt 中如何减轻服务端渲染压力？SSG 和 ISR 是什么？

核心思路是减少每次请求都重新渲染页面的次数，按页面的数据更新频率、SEO 需求和个性化程度选择渲染方式。

| 方式 | 什么时候生成 HTML | 如何减轻服务端压力 | 适用场景 |
| --- | --- | --- | --- |
| SSR（服务端渲染） | 未命中缓存时，在请求阶段渲染 | 配合页面缓存、接口缓存减少重复计算 | 需要实时数据或个性化内容的页面 |
| SSG（静态站点生成） | 构建时提前生成 | 请求直接获取静态文件，无须现场渲染 | 官网介绍、文档等更新较少的页面 |
| ISR（增量静态再生） | 按需生成并缓存，按规则重新生成 | 多个请求复用页面缓存，减少重复渲染 | 博客、商品介绍等允许短暂旧数据的公共页面 |
| CSR（客户端渲染） | 浏览器中渲染 | 把页面渲染工作交给客户端，但接口仍有开销 | SEO 要求较低的后台页面 |

**SSG：构建时生成，请求时直接读取。**

例如官网介绍页，发布时就生成 HTML，用户访问时由静态服务器或 CDN 返回。内容更新通常需要重新构建发布；动态路由要确保在构建时被发现或显式列入预渲染范围。

**ISR：生成结果可以复用，也能逐步更新。**

例如给博客页设置一小时缓存：首次访问生成页面，后续请求读取缓存；缓存过期后，由后续请求触发后台重新生成，期间可以先返回旧页面。它减少了每次请求的渲染开销，也避免了内容变化就重建全站。缓存时间到期不等于定时任务主动刷新。

下面是 Nuxt 3/4 使用 `routeRules` 配置混合渲染的示例：

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  routeRules: {
    '/': { prerender: true }, // 构建时预渲染
    '/about': { prerender: true },
    '/blog/**': { isr: 3600 }, // 支持的平台上使用 ISR，缓存一小时
    '/products/**': { swr: 600 }, // 缓存响应，过期后在后台更新
    '/admin/**': { ssr: false }, // 后台页面使用客户端渲染
  },
});
```

Nuxt 的 `isr` 与 `swr` 都可以复用响应并在过期后更新；`isr` 还利用支持平台的 CDN 缓存，官方文档列举了 Vercel 和 Netlify。自建 Node 服务可考虑 `swr`，多实例部署时还要规划共享缓存。ISR 需要相应运行时或平台能力，不能仅靠纯静态文件托管实现更新。

此外，还可以缓存公共接口数据、并行请求互不依赖的数据、减少首屏不必要的请求和计算。用户专属内容不能直接放进所有人共用的页面缓存，应跳过公共缓存，或按用户正确隔离。

**面试回答：**我会优先按页面选择渲染方式，而不是所有页面都逐次 SSR。变化少的页面用 SSG，构建时生成静态文件；允许短暂旧数据的公共页面用 ISR，复用生成结果并按需更新；实时或个性化页面保留 SSR，配合合适的数据缓存；后台页面可以用 CSR。在 Nuxt 中可以通过 `routeRules` 做混合渲染，同时确认部署平台是否支持 ISR。

参考：[Nuxt 官方文档：Rendering 与 Route Rules](https://nuxt.com/docs/4.x/guide/concepts/rendering)

### 4. NestJS 中的管道（Pipe）是什么？

管道是在控制器路由方法执行前，对传入参数进行处理的机制，主要用于**类型转换**和**数据校验**。

- **类型转换**：例如把 URL 参数中的字符串 `'123'` 转换为数字 `123`。
- **数据校验**：检查参数是否符合规则；不符合时抛出异常，阻止控制器方法执行。

**示例一：使用内置管道转换参数。**

```ts
import { Controller, Get, Param, ParseIntPipe } from '@nestjs/common';

@Controller('users')
export class UsersController {
  @Get(':id')
  findOne(@Param('id', ParseIntPipe) id: number) {
    return { id };
  }
}
```

访问 `/users/123`，方法收到的 `id` 是数字 `123`；访问 `/users/abc`，管道会抛出异常，默认返回 400。只写 `id: number` 不会自动转换请求参数，因为 TypeScript 类型标注在运行时不存在。

**示例二：使用 `ValidationPipe` 校验请求体。**

常见做法是安装 `class-validator` 和 `class-transformer`，用 DTO 类声明校验规则，再注册全局校验管道：

```ts
// create-user.dto.ts
import { IsInt, IsString, Min } from 'class-validator';

export class CreateUserDto {
  @IsString()
  name: string;

  @IsInt()
  @Min(0)
  age: number;
}

// main.ts：创建 app 后配置
app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true, // 移除没有校验装饰器的属性
    transform: true, // 将普通请求对象转换为 DTO 类实例
  }),
);

// 控制器方法中使用 DTO
@Post()
create(@Body() body: CreateUserDto) {
  return body;
}
```

例如传入 `{ "name": "小明", "age": -1 }` 会校验失败。`transform: true` 不代表 DTO 中所有属性都会自动转换类型；需要把请求体中的字符串年龄转换为数字时，可以显式使用 `@Type(() => Number)` 等转换规则。

管道可以绑定在参数、方法、控制器或全局范围。自定义管道通常是一个带 `@Injectable()` 装饰器、实现 `PipeTransform` 接口的类，在 `transform(value, metadata)` 中返回处理后的值，或抛出异常。

**面试回答：**NestJS 的管道是在控制器方法执行前处理入参的机制，主要负责类型转换和数据校验。例如 `ParseIntPipe` 把路由参数转成整数，`ValidationPipe` 根据 DTO 规则校验请求数据。处理成功后把参数交给控制器，失败则抛出异常，控制器方法不会执行。它可以局部使用，也可以全局注册。

参考：[NestJS 官方文档：Pipes](https://docs.nestjs.com/pipes)
