# AI Coding：如何选择自测框架

让 AI 写完一个页面之后，如何确认它真的能用？

最常见的做法是让 AI 检查代码、执行构建，再打开浏览器点一下。但构建成功只能说明代码可以被编译，页面能打开也不代表搜索条件正确、保存成功或者权限生效。

自测需要把“看起来没问题”转换成可以执行、可以重复验证的检查。AI 可以帮助分析场景、编写测试、执行测试和分析失败，而测试框架负责运行操作、执行断言并记录结果。

选型时，先明确要验证哪一层，再选择工具。

## 1. 自测框架有哪些

前端开发中的自测通常涉及以下几类工具。它们解决的问题不同，可以组合使用。

| 测试类型 | 常见工具 | 验证内容 | 运行环境 |
| --- | --- | --- | --- |
| 单元测试 | Vitest、Jest | 金额计算、数据转换、状态判断等函数逻辑 | 通常为 Node.js，也可配置浏览器环境 |
| 组件测试 | Vue Test Utils + Vitest、React Testing Library、Cypress Component Testing | 表单校验、弹窗、组件事件等行为 | 模拟 DOM 或真实浏览器，取决于方案 |
| 浏览器 E2E | Playwright、Cypress、Selenium / WebdriverIO | 打开页面、登录、搜索、保存等完整用户流程 | 真实浏览器 |
| 接口测试 | Apifox、Postman / Newman、Playwright 的 APIRequestContext | 直接请求后端，检查响应与业务流程 | HTTP 客户端，无需打开页面 |
| App 自动化 | Appium、Maestro | 原生 App、真机或模拟器中的交互流程 | App 与设备环境，WebView 支持需按工具核实 |

这里的“真实浏览器”也包括无界面模式。无界面模式下仍然运行浏览器引擎，执行 JavaScript、渲染页面和发送请求，只是不会显示浏览器窗口。

ESLint、类型检查和构建同样值得让 AI 执行，但它们分别检查代码规则、类型和编译过程，无法替代业务行为测试。

## 2. 浏览器 E2E 应该怎么选

如果目标是“让 AI 打开页面，模拟用户操作，检查接口和页面结果”，应该重点比较浏览器 E2E 工具。

| 工具 | 主要特点 | 适合的场景 |
| --- | --- | --- |
| Playwright | 支持 Chromium、Firefox、WebKit，提供移动端模拟、接口拦截、自动等待和 Trace | 新项目、跨浏览器回归、移动 H5、CI 中的自动化测试 |
| Cypress | 交互式调试直观，同时提供组件测试与 E2E 能力 | 重视本地可视化调试，或已有 Cypress 用例的团队 |
| Selenium / WebdriverIO | WebDriver 生态成熟，可结合浏览器网格及设备平台 | 已有相关基础设施、需要接入现有自动化体系的团队 |
| Puppeteer | 浏览器控制灵活，更偏自动化工具库 | 截图、抓取、生成 PDF 等定制任务；作为完整测试体系需补充测试运行与报告等设施 |

对于 Vue + Vite 的 H5 项目，我倾向于先选择 Playwright。它可以同时完成页面交互、请求检查和失败追踪，也适合让 AI 通过命令执行已有 spec。

如果项目已经有维护良好的 Cypress 或 Selenium 测试，不必为了引入 AI 更换框架。现有测试是否可靠、能否稳定执行，比工具名称更重要。

## 3. 打开真实浏览器，不等于请求真实后端

这是理解 E2E 时容易混淆的一点。同样使用 Playwright，可以采用三种不同的接口策略。

| 策略 | 页面如何运行 | 接口如何处理 | 能证明什么 |
| --- | --- | --- | --- |
| 完整 Mock | 实际加载前端页面 | 拦截业务请求，返回预先准备的数据 | 给定响应下，前端交互、参数和状态处理符合预期 |
| 部分 Mock | 实际加载前端页面 | 部分请求模拟，其余请求后端 | 未模拟链路的联通性，以及模拟场景下的前端行为 |
| 真实接口联调 | 实际加载前端页面 | 请求测试环境的真实后端 | 当前环境、账号和数据条件下，前后端流程可以协同工作 |

Mock 测试中，页面仍然会执行请求代码，只是请求被测试工具接住，后端没有实际处理。

例如模拟接口返回一条奖励记录，可以验证奖励名称、数量和领取按钮是否正确展示；模拟保存失败，可以验证错误提示和输入内容是否保留。

但这不能证明真实后端返回了正确字段，也不能证明奖励确实发放。

真实接口联调可以发现字段变化、权限不匹配、保存未生效等问题，但需要可用的后端、账号和测试数据。两种策略各有用途：用 Mock 稳定覆盖边界场景，用真实接口验证关键业务链路。

另外，spec 没有写 Mock，不代表请求一定到达了真实业务服务。还需要检查前端代理、网关和目标环境，确认整条链路没有接入其他模拟服务。

## 4. 登录方式取决于产品

### 管理后台：填写真实登录表单

后台通常有账号密码登录页。测试可以像用户一样输入账号密码、点击登录，等待前端完成跳转。

建议把这段逻辑放在公共 helper 中，供多个 spec 复用。测试数量较多时，也可以通过 setup 项目登录一次，再用 `storageState` 为后续测试提供初始登录状态。

需要注意，默认的 `storageState` 不保存 `sessionStorage`。如果项目依赖它保存登录信息，就需要额外处理。复用登录态的业务用例，也不能代替针对登录流程本身的测试。

### App 内嵌 H5：提供有效的用户凭证

活动 H5 往往没有登录页，而是从 App 原生桥获取 `uid`、`ticket` 和语言。

如果页面已有浏览器调试入口，可以使用测试账号的有效凭证打开页面。例如以下仅为入口形式示意，参数应以项目实现为准：

```text
/#/activity?dev=1&uid=TEST_UID&ticket=VALID_TICKET&lang=zh
```

`dev=1` 只是让页面读取调试参数，不会生成有效身份，也不代表接口一定切到了测试环境。凭证有效性和后端地址需要分别确认。

另一种方式是在页面初始化前模拟原生桥，让前端取得有效的测试凭证。这属于模拟宿主能力，后续业务请求仍然可以连接真实后端。

账号与凭证可以通过环境变量或不提交 Git 的本地配置集中管理，并留意 URL、日志和 Trace 中可能记录的敏感信息。

## 5. 断言质量决定自测是否有意义

“执行成功”与“业务正确”之间，隔着具体的断言。

比如搜索用户后，仅检查表格可见：

```ts
await expect(page.locator('.vxe-table')).toBeVisible()
```

即使前端漏传了用户 ID，接口返回的是未筛选列表，这个检查仍然可能通过。

更有价值的检查应当包括：请求是否带上指定 ID，业务响应是否成功，返回记录是否匹配条件，以及页面是否正确展示记录。真实接口返回的数据，也需要有已知预期才能判断对错。

| 操作 | 建议验证的结果 |
| --- | --- |
| 搜索 | 请求参数正确，返回记录符合条件，页面展示对应结果 |
| 保存 | 请求字段正确，业务响应成功，重新查询同一条记录后值已更新 |
| 切换大区 | 请求路径、区域参数或请求头正确，后续编辑绑定正确区域 |
| 权限不足 | 对应入口受限；后端权限另需通过真实接口测试验证 |
| 接口失败 | 显示明确提示，输入不丢失，重试行为符合预期 |

AI 生成测试时，还要特别检查下面这种写法：

```ts
if (!drawerOpened) {
  console.log('编辑抽屉打开失败，跳过')
  return
}
```

普通 `return` 会让用例正常结束，可能被统计为通过。抽屉打不开属于验证失败，应该使用断言；确实缺少前置条件时，应明确标记为跳过并记录原因。

同样，收集了 `issues` 却只打印日志，也不会让测试失败。重试次数和固定延时无法弥补这些断言缺失。

## 6. AI 自测如何形成可重复的流程

AI 直接操作浏览器适合探索：发现布局异常、尝试未预设的交互、观察控制台和网络错误。固定 spec 则适合把已知业务规则重复验证。两者可以结合使用。

一个可落地的流程是：

1. **读取需求与实现**：分析页面、接口文档、表单字段、权限和状态流转，列出要验证的行为。
2. **执行静态检查**：运行项目已有的 lint、类型检查和构建，先处理基础错误。
3. **执行浏览器测试**：用 Mock 覆盖异常场景，用真实测试环境验证关键流程。
4. **分析失败证据**：结合断言、请求响应、控制台和 Trace 定位原因，区分代码问题与环境阻断。
5. **沉淀回归用例**：将有价值的探索发现转成固定测试，并在修复后重新验证。

真实写入应使用专用测试记录，避免随机修改列表第一条业务数据。需要清理或恢复时，应把它设计进测试流程；并发测试也要避免争用同一条记录。

测试报告需要说明哪些场景使用了 Mock、哪些连接了真实后端、哪些跳过或被环境阻断。测试了一个页面，不应得出整个系统已经验证通过的结论。

## 7. Vue H5 项目的选择建议

对于页面交互和接口调用较多的 Vue H5 活动项目，可以从较小的组合开始：

| 当前需求 | 建议 |
| --- | --- |
| 验证首页、榜单、记录、领取等用户流程 | Playwright，优先覆盖测试环境中的关键链路 |
| 稳定复现空数据、超时、失败和特殊活动状态 | 在 Playwright 中使用 Mock |
| 验证金额计算、奖励规则、数据转换 | 有实际复杂度时补充 Vitest |
| 独立验证接口协议与后端流程 | 使用 Apifox，或 Playwright 的 HTTP 测试能力 |
| 验证充值跳转、原生桥、WebView 与真机兼容性 | 在实际 App 内补验，规模扩大后再考虑 Appium 等方案 |

移动端模拟能够覆盖视口、触摸和部分设备特征，但桌面浏览器中的模拟无法完整代表真实手机与 App WebView。

现阶段先建立 Playwright 的少量关键用例，比同时安装多套测试工具更容易获得反馈。随着业务逻辑复杂度和回归成本增长，再补充单元测试、组件测试或 App 自动化。

选择框架的依据，是要验证的业务行为、运行环境和维护成本。AI 可以降低编写测试的成本，但验收标准、测试数据和结果证据仍然需要明确。
