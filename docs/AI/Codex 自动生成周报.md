# Codex 自动生成周报

每周写周报，我都会重新翻一遍 Git 提交，再去 Jira 确认需求到了哪个阶段。如果一周的工作分散在几个后台、活动平台和文档仓库里，单看某个项目很容易漏掉内容。

周报格式确定后，就可以将整理流程设置为每周五上午 10 点自动执行。设置任务时，需要确认保存位置、执行环境，以及离开当前聊天后能否继续运行。这也涉及 ChatGPT「定时任务」与 Codex 自动化的区别。

本文记录三个问题：定时任务是什么、ChatGPT 与 Codex 的相关功能有什么区别，以及如何把一次周报整理变成可重复执行的任务。

## 一、定时任务是什么

定时任务就是把一件工作和执行时间一起保存，到约定时间再执行。它既可以只执行一次，也可以按天、周等周期重复执行。

在 AI 产品里，除了执行时间，还要保存任务指令。每次触发后，AI 根据指令读取资料、调用工具并生成结果。

例如，下面两种要求的执行内容不同：

| 要求 | 到时间后需要做什么 |
| --- | --- |
| 每周五提醒我写周报 | 发送提醒 |
| 每周五读取我的 Git 提交和 Jira，生成周报 | 查询数据、核对状态、归并工作，再输出周报 |

自动生成周报属于第二种，需要明确数据来源和整理规则。设置时可以拆成五项：

1. **时间**：什么时候执行，使用哪个时区。
2. **范围**：统计哪段时间、哪些项目、谁的工作。
3. **数据**：从 Git、Jira 或其他服务读取什么。
4. **处理规则**：如何去重、归类，以及哪些内容不计入。
5. **交付**：使用什么格式，结果放在哪里。

只写“每周给我一份周报”，后面四项都可能产生歧义。

## 二、ChatGPT「定时任务」和 Codex 自动化有什么区别

OpenAI 帮助中心区分了 ChatGPT 定时任务与 Codex 自动化。选择时，关键是**任务在哪个环境运行，以及那个环境能访问哪些数据**。[官方说明](https://help.openai.com/zh-hans-cn/articles/10291617-scheduled-tasks-in-chatgpt)

下面按常见使用方式比较：

| 对比项 | ChatGPT 网页端定时任务 | 本次 Codex 桌面端本地自动化 |
| --- | --- | --- |
| 任务环境 | ChatGPT 在线环境 | 电脑上的 Codex 工作环境 |
| 数据来源 | 任务可用的在线上下文和已连接工具 | 本机文件、Git 仓库、可用命令与已接入工具 |
| 本机路径 | 不能仅凭路径直接读取电脑目录 | 可以在权限范围内读取指定目录 |
| 适用示例 | 定期资讯、提醒、基于在线资料生成摘要 | 多仓库提交汇总、项目检查、结合本地资料整理报告 |

### 1. 不要只看入口名称

最新官方指南中，桌面端相关能力也会出现在统一的 Scheduled / 定时任务入口下。因此，“界面叫定时任务”并不足以确定执行方式，应该继续看任务详情中的项目、运行环境和结果去向。[定时任务指南](https://learn.chatgpt.com/docs/automations?surface=app)

同样，也不适合简单理解成“ChatGPT 只能提醒，Codex 只能写代码”。生成周报属于内容整理，但如果输入来自本机代码仓库，本地自动化就很合适。

### 2. 数据在哪里，往往决定用哪一种

这次的输入有两部分：

```text
本机多个 Git 仓库 → 本周实际提交了什么
Jira 工单         → 需求标题、链接和当前状态
```

本机还有尚未推送的提交，Jira 则通过已经配置好的 MCP 查询。沿用当前 Codex 工作环境，可以直接复用这条读取链路。

如果以后把提交数据放到在线服务，并在相应任务环境中配置好访问能力，也可以重新评估在线执行方案。把本机绝对路径复制到在线任务提示词里，并不会自动建立访问能力。

Jira 接入过程见：[Codex 接入自建 Jira](</AI/Codex 接入自建 Jira.md>)。

## 三、先验证周报整理流程

创建定时任务前，先整理一次周报，验证数据是否完整、统计口径是否准确。本次统计覆盖多个业务仓库及文档库，以已提交的工作为范围，再按需求归并。

以下规则也需要写入定时任务指令。

### 1. 已提交不等于已上线

统计范围包括功能分支中的提交，也包括尚未推送或尚未上线的工作。提交说明比较模糊时，需要看实际差异，不能仅凭“暂存”两个字推断完成了某项功能。

周报中也要区分状态：Git 证明有代码提交，Jira 则记录工单当前处于待测试、待验收或已关闭等阶段。

### 2. 多仓库和子模块要分别检查

一个主仓库可能通过 Git 子模块接入多个后台。只查主仓库日志，可能只能看到子模块引用更新，读不到后台内部的业务提交。

整理时需要分别检查各个独立 Git 仓库，再把同一需求的代码、修复和文档记录合并成周报条目。

### 3. 同一项工作只写一次

一个需求可能包含开发、联调修复、合并测试分支和文档更新，也可能因为 cherry-pick 出现多个不同提交号。

周报按工作内容归并，避免把这些记录重复算成多个成果。文档可以补充交付证据，无需每个文档提交都单列一项。

### 4. Jira 不只查当前经办人

开发完成后，工单经办人可能已经转给测试或产品。如果只查询当前分配给自己的工单，反而会漏掉本周刚完成的工作。

查询时结合两条线索：提交中关联的工单，以及本周曾分配给自己的工单。查询得到的待开发事项，可作为下周计划建议；没有本周工作证据时，不放进本周成果。

## 四、先确认输出格式，再固定执行

周报按需求逐条列出，每条包含标题、链接和当前状态。先确认输出格式，再将其写入任务指令，便于每周沿用。

格式示例如下，工单和链接均为占位内容：

```markdown
**本周工作计划：**

1. [【技术优化】后台页面迁移](https://jira.example.com/browse/PROJ-101)（待测试）
2. [【WEB】新增业务配置](https://jira.example.com/browse/PROJ-102)（待验收）
3. [【问题修复】批量导入错误提示](https://jira.example.com/browse/PROJ-103)（已关闭）
4. 【后台优化】菜单顺序及滚动问题修复（已提交）

**下周工作计划（建议）：**

1. [【WEB】待开发需求](https://jira.example.com/browse/PROJ-104)（待开发）
2. 【测试跟进】跟进本周需求测试和验收。
```

本周部分列出已开展的工作和当前状态，下周部分根据待办事项给出建议，具体安排再按实际情况调整。

## 五、如何设置这次定时任务

### 1. 确定时间与统计边界

最终设置为：

| 项目 | 本次设置 |
| --- | --- |
| 频率 | 每周五 |
| 时间 | 上午 10:00 |
| 时区 | Asia/Shanghai，北京时间 |
| 统计区间 | 本周一 00:00 至本次运行时间 |
| 结果去向 | 返回创建任务的当前聊天 |

需要注意：周五上午生成的报告，只覆盖到运行时刻。周五下午才提交的内容，不会出现在当天上午已经生成的结果里。如果希望覆盖整个周五，可以调整执行时间或统计区间。

### 2. 编写完整的任务指令

下面是根据本次任务整理的可复用提示词。使用前替换目录、账号和项目范围：

```text
请创建一个每周周报定时任务。

执行时间：每周五上午 10:00，时区 Asia/Shanghai。
每次结果返回当前聊天。

每次执行时：
1. 统计本周一 00:00 至运行时刻的工作。
2. 读取 /path/to/workspace 下指定业务仓库、独立子模块及文档库的 Git 提交。
   核对我的作者姓名和邮箱，检查所有本地分支及已有远程跟踪引用。
   功能分支、尚未推送或尚未上线的已提交工作都计入。
   对说明模糊的提交检查实际差异，不把别人的工作算给我。
3. 合并重复合并、cherry-pick 和同一需求的修复，按工作内容归并。
4. 查询提交关联的 Jira 工单，以及本周曾分配给我的工单。
   使用真实标题、链接和当前状态；当前经办人可能已变成测试或产品。
   无本周工作证据的待开发工单，不计入本周成果。
5. 输出“本周工作计划：”，使用编号列表。
   每条为【类别】工单标题链接（当前状态）。
   无工单的后台优化可合并成一条，注明“已提交”。
6. 输出“下周工作计划（建议）：”，结合待开发、待测试和待验收事项给出简短建议。
7. 排除技术学习及学习文档，不展开代码细节，不把已提交写成已上线。
8. 只读整理，不修改代码、Git 状态或 Jira，不向其他人发送消息。
   数据源不可用时明确说明缺失，不编造结果。
```

这里所说的“检查所有分支”，仍然受本机已有 Git 引用范围限制。远端尚未同步到本机的分支和提交，不能保证被发现；有这类需求时，应另行明确是否允许自动 fetch。

### 3. 确认任务确实保存

创建后，在任务面板中检查启用状态，并核对任务名称、执行周期、指令和关联聊天。本次也检查了本地配置，确认这些设置已保存。

本机观察到的配置位置为：

```text
~/.codex/automations/<任务 ID>/automation.toml
```

这是本次桌面端环境中的实际保存位置，不应当作所有版本和在线任务通用的目录。日常修改优先通过任务面板或对话操作，无需手动编辑配置文件。

## 六、聊天、任务和执行环境是三个不同的问题

离开当前聊天后，任务是否继续执行，需要分别看任务状态、结果去向和运行环境。

**切换到别的聊天**，只是没有查看原聊天，并不等于删除任务。当前任务已经保存，不需要为了它一直停留在同一个页面。

**任务结果返回哪里**，由任务设置决定。本次关联当前聊天；如果希望每周结果独立展示，应明确要求每次运行新建聊天，并检查任务详情是否符合预期。

**本机能否执行**，取决于运行环境。需要读取本机文件的任务，应保持电脑开机、应用运行，仓库与 Jira 连接也要可用；不能把“无需打开这个聊天页面”理解成“关机后仍可读取本机仓库”。[本地任务执行说明](https://learn.chatgpt.com/docs/automations?surface=app)

另外，不宜随意删除关联聊天。ChatGPT 帮助中心明确说明，删除关联聊天会暂停其定时任务；本次 Codex 本地任务的具体行为，应以对应版本的任务面板为准，不能直接套用另一产品的规则。[ChatGPT 任务与聊天的关系](https://help.openai.com/zh-hans-cn/articles/10291617-scheduled-tasks-in-chatgpt)

## 七、创建成功之后，还要检查第一次运行

本次已完成周报整理流程验证、输出格式确认、任务创建和配置核对。**写这篇文章时，还没有验证首次自动运行的结果。**

首次自动运行后，需要重点检查：

- 是否按北京时间周五 10 点触发，并覆盖预期统计区间。
- 是否读到了各个独立仓库，Git 作者过滤是否准确。
- Jira 查询是否成功，已转交测试的工单有没有遗漏。
- 是否合并了重复提交，并排除了技术学习内容。
- 输出格式和结果去向是否符合约定。

如果结果有偏差，再修改已保存的任务指令。创建成功只说明调度配置已保存；数据访问、工具连接和输出质量，还需要实际运行来确认。
