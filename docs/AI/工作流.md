# 我的 H5 活动 AI 开发工作流

这是我 2026 年入职后，结合公司 H5 营销活动开发整理的一套 AI 工作流，下文称为“巨鲸工作流”。

日常开发涉及多个平台：原型和设计稿在蓝湖，接口文档使用 Knife4j，多语言翻译和 Bug 记录在飞书。开发过程中，需要不断读取、整理和核对这些信息。换一个活动或开启新的 Agent 对话后，还需要重新交代项目背景。

我希望把这些重复操作整理成可复用的流程，让 Agent 能够获取资料、执行任务，并把结果保存到项目中，方便后续继续使用。

## OpenSpec 规范驱动开发

OpenSpec 可能是 26 年最火的一个点，很多公司通过引入 OpenSpec 规范驱动开发，来提升开发效率。

OpenSpec 规范驱动开发这种模式并不适合语聊业务开发，更严格来讲是不适合 H5 营销活动的开发，在当前业务中，每次 H5 活动相对独立，活动之间的业务关联有限。

虽然 OpenSpec 规范驱动开发这种模式并不适合语聊业务开发，但这种开发流程实际上还是通过 LLM 上下文提示以及 Skill 插件来实现的原理。

于是我基于 OpenSpec 的原理，结合语聊业务开发的需求，设计了一套适合语聊业务开发的工作流。

## Harness Engineering 

Harness 的核心公式很简单 `Agent = Model + Harness`。本质上是一种设计模式或者思想，后面的工作流设计都有涉及到。

## 蓝湖 MCP

蓝湖 MCP 是 巨鲸工作流不可缺失的工具，它是自己开发的一套工具，灵感来源于 Figma MCP。

前端开发强依赖蓝湖设计稿，但 Cursor 等 AI Agent 助手无法直接访问蓝湖平台，设计信息只能靠人工截图，还原效率低，而且不准确。为此独立开源了 lanhu-node 工具，基于
MCP 将蓝湖设计协作平台接入 Cursor，目前支持 UI 设计稿还原，Axure 原型解析，批量下载切图等。

## 巨鲸工作流

这套工作流覆盖从需求理解到发布的主要环节。各个阶段的输入、自动化处理和人工确认如下：

| 阶段 | 输入 | 自动化处理 | 产出 | 人工确认 |
| --- | --- | --- | --- | --- |
| 原型解析 | 蓝湖原型链接 | 读取活动规则、页面流程并整理到本地 | `prototype.md` | 需求理解是否准确，有没有遗漏或歧义 |
| 设计稿还原 | 蓝湖设计稿、原型说明 | 获取设计信息、下载切图、编写页面和拆分组件 | 页面代码、组件和素材 | 页面结构与交互是否符合需求 |
| 还原审核 | 设计稿、已实现页面 | 截图、提取页面快照、对比差异 | 截图、快照和审核报告 | 差异是否成立，哪些需要继续调整 |
| 多语言处理 | 英文文案、飞书翻译表 | 按规则导出和导入翻译，汇总变更 | 语言文件和变更报告 | 翻译是否完整，页面展示是否正常 |
| 接口对接 | Knife4j 接口文档 | 同步和查询接口文档，完成接口接入 | `api-docs.json`、接口调用代码 | 业务流程和异常情况是否符合预期 |
| Bug 修复 | 飞书中当前活动的问题记录 | 读取问题并修改对应代码 | 代码修改和处理结果 | 问题是否解决，由谁验证和关闭 |
| 提交与部署 | 待提交代码 | 执行代码检查，按项目配置构建和部署 | 提交记录、构建结果和部署通知 | 检查结果及发布环境是否正确 |

表格按常见开发顺序排列，各个环节也可以根据活动进度单独执行。前一步保存下来的文档和代码，会作为后续任务的输入，减少重复描述项目背景的成本。

### 原型

活动原型是一切开发工作的起点，通过原型可以快速理解活动需求，明确活动流程。

一份标准的原型链接如下：
```text
https://lanhuapp.com/web/#/item/project/product
  ?tid=2d185eaa-803c-4a3b-8985-c8982d3d83ed
  &pid=f30c9cac-fc1c-42c6-ae01-592938226141
  &docId=077bbf6d-6dd1-4359-836e-7bbf74db2603
  &image_id=077bbf6d-6dd1-4359-836e-7bbf74db2603
  &pageId=06ef22a06ea7453a8886f3a70e7b7e8e
  &versionId=14f77309-636c-4fd7-a7d6-b62c1cc91c63
  &docType=axure
```

这里补充对蓝湖URL路径的说明，因为lanhu-mcp解析URL路径需要这些参数。有时候会因为少了某个字段导致解析失败，我后面加了一份`my-lanhu-mcp.mdc`进行字段的补充。

| 参数 | 含义 | 必填 | 说明 |
|------|------|------|------|
| **tid** | 团队 ID | 原型场景必填 | 别名 `teamId` / `team_id` |
| **pid** | 项目 ID | **必填** | 别名 `project_id` |
| **docId** | 文档 ID | 列页/下载/分析必填 | 一份 PRD/原型包的唯一标识 |
| **image_id** | 与 docId 同义 | 可选 | 蓝湖 API 常用参数名；解析时 `docId ?? image_id` |
| **pageId** | 页面节点 ID | 可选 | sitemap 中 `pages[].id`；URL 表示蓝湖 UI 当前选中的页 |
| **versionId** | 文档版本 | 可选 | URL 可带；**下载/截图缓存以 API 返回的 latest version 为准** |
| **docType** | 文档类型 | 可选 | 如 `axure`；目前解析保留，业务未单独分支 |

这里直接把从蓝湖复制的完整原型链接交给 Agent，由 lanhu-mcp 解析链接中的团队、项目和文档信息。

对话如下：

```text
看下这个沙特国庆的原型<蓝湖原型完整链接>
```

然后 Agent 会调用 lanhu-mcp 获取原型信息，并返回给用户。

![原型截图](/public/assets/ai/工作流1.png)

因为 Cursor Agent 更换窗口后上下文会丢失，所以需要将原型信息保存到本地，方便后续使用。

这里使用 Skill 来实现原型信息保存到本地。在`.cursor/skills`目录下创建一个`Axure`文件夹，文件夹内创建一个`SKILL.md`文件，文件内容大致如下：

```md
# Axure
通过 lanhu-mcp 获取原型后，判断当前活动，然后在当前活动目录下创建一个`prototype.md`文件，文件内容为原型信息。
```

这样子每一个活动都有一个对应的原型信息文件，方便后续使用。

这里以沙特国庆为例，当前的目录结构为`ksa/prototype.md`。文件内容大致如下：

```md
# 沙特国庆活动-原型说明
## 活动概览
## 一、活动规则
## 二、祝福板
## 三、升国旗
## 四、守护者联盟
## 五、活动礼物
## 六、活动物料
## 组件划分说明
```

### 设计稿

有了原型后，接下来就是设计稿了。同样的，我们也是把链接给到 Agent 调用 lanhu-mcp，对话如下：

```text
看下这个沙特国庆的设计稿
```

然后 Agent 会调用 lanhu-mcp 获取设计稿信息，并返回给用户。

Agent 接手后，开始批量下载切图到`ksa/assets`目录下，并且在`ksa/index.vue`开始还原设计稿，组件拆分在`ksa/components`目录下。

### 还原审核

这里的设计稿还原能达到80%的还原度，剩下的20%需要人工进行调整。

#### playwright截图

为了进一步提升还原度，使用 playwright 进行截图，并对比设计稿，找出差异点，进行 AI 调整。

这里需要安装下 Playwright MCP 插件，并编写对应的 Skill 来实现截图功能。在`.cursor/skills`目录下创建一个`Playwright`文件夹，文件夹内创建一个`SKILL.md`文件，文件内容大致如下：

```md
# Playwright
本项目 H5 页（750 设计稿）的 Playwright MCP 工具规范
## 配置
## 工具约定
## 快照
## 归档
```

另外由于每一个项目不同，所以 playwright 的配置需要根据项目进行调整。为此 在`.cursor/skills/Playwright`目录下创建一个`config.json`文件，文件内容大致如下：
```json
{
  "browser": {
    "contextOptions": {
      "viewport": { "width": 375, "height": 812 },
      "deviceScaleFactor": 2,
      "isMobile": true,
      "hasTouch": true
    }
  },
  "snapshot": { "mode": "full", "boxes": true }
}
```
这里需要注意，开启快照`.yml`，方便通过无障碍树的模块/文案/列表结构对照。

#### 审核

对照蓝湖设计稿审核已还原的 H5 页面，按状态整页截图+快照、对齐 750/375、写出 P0/P1/P2 报告。在`.cursor/skills`目录下创建一个`design-review`文件夹，文件夹内创建一个`SKILL.md`文件，文件内容大致如下：

```md
# 设计稿还原审核
对照蓝湖设计稿审核已还原的 H5 页面，按状态整页截图+快照、对齐 750/375、写出 P0/P1/P2 报告。
## 前置
## 采图
## 怎么比
## 产出
```

这里会把设计稿还原的 H5 页面截图，并对比设计稿，找出差异点，产出报告`审核.txt`到`ksa/`目录下，然后根据报告进行人工调整。

#### 人工调整

经过上面的工序后，简单的页面基本可以完成，剩下的就是一些复杂的页面（例如三段式背景图片），需要人工进行调整。

### 多语言-国际化

目前页面基本都是英文，需要进行多语言翻译。

这里使用`rule`实现就可，在`.cursor/rules`目录下创建一个`i18n.mdc`文件，文件内容大致如下：

```md
# i18n 
## 语言与文件
## 模块定义
## 新增 key 规则
## 行序规则（导出与导入共用）
## 导出格式
```

多语言处理分为导出和导入两个阶段：

1. 前端提取当前活动的英文文案，按模块导出，并保留每条文案对应的代码 key。
2. 活动运营在飞书翻译表中补充其他语言。
3. Agent 读取翻译表，按照约定的映射关系，将各语言写入对应的 vue-i18n 文件。
4. 导入完成后输出变更报告，列出修改、未变更、遗漏和异常的条目，供人工核对。

英文原文作为翻译依据，代码 key 用于定位具体条目。例如，`sheepTreasure.claim` 对应的英文文案是 `Claim`。这样在文案修改时，也能明确知道需要更新哪个模块下的哪一项。

导入完成后，变更报告示例如下：

````md
## 变更报告（导入完成后必须输出）

首行标明模块名，再用表格汇总：

| Key | 语言 | 旧值 | 新值 |
|-----|------|------|------|
| `sheepTreasure.claim` | en | `Claim` | `Collect` |
| `sheepTreasure.goComplete` | ar | `...` | `...` |

并附摘要：

```text
模块：sheepTreasure
共 N 条翻译
- 英文修改：X 条
- 阿拉伯语修改：Y 条
- 未变更：M 条
- 跳过/异常：K 条（说明原因）
- 导出后新增未导入：P 条（列出 key）
```
````

### 接口对接联调

这边的接口文档使用 Knife4j 生成， 可以通过本地配置`API_DOCS_URL`来访问接口文档。

为了避免每一次都去拉取接口文档，这里使用脚本拉取接口文档到本地`api-docs.json`文件。同时优化查询速度，支持关键词查询。

在`package.json`中添加如下配置：
```json
{
  "scripts": {
    "api-docs:sync": "node scripts/api-docs.mjs sync",
    "api-docs:query": "node scripts/api-docs.mjs query"
  }
}
```

然后创建 `scripts/api-docs.mjs`，负责同步接口文档，以及按关键词查询本地文档。脚本通过两个命令入口供开发者和 Agent 使用：

```bash
# 从后端同步最新接口文档，保存到 api-docs.json
npm run api-docs:sync

# 按接口路径查询
npm run api-docs:query -- /h5/eid/lottery

# 按数据模型名称查询
npm run api-docs:query -- ZaishengHomeVo

# 按关键词查询
npm run api-docs:query -- eid
```

同步地址通过环境变量 `API_DOCS_URL` 配置。日常对接先查询本地文档，接口发生变化时再重新同步。

脚本实现以及配套的 Rules、Skills 配置，见另一篇文章 [ai-api-docs](./ai-api-docs.md)。

`api-docs.json`是一份swagger的json文件，包含了所有的接口信息。
```json
{
  "swagger": "2.0",
  "info": {
    "version": "1.0.0",
    "title": "API Documentation"
  },
  "basePath": "/api",
  "paths": {
    "/h5/eid/lottery": {}
  }
}
```

为了配置 AI Agent 使用，在`.cursor/skills`目录下创建一个`api-docs`文件夹，文件夹内创建一个`SKILL.md`文件，文件内容大致如下：

```md
# API 文档工作流
通过 Knife4j 生成接口文档，并保存到本地`api-docs.json`文件。
## 何时查询（query）
## 何时更新（sync）
## AI 对话集成方式
```

这样子 AI Agent 就可以通过`npm run api-docs:sync`来拉取接口文档，并保存到本地`api-docs.json`文件。

接口联调这一块相对轻松，只要后端给到的接口文档清晰没问题，基本不用返工。

### Bug 修复

Bug 修复这一块，主要是在飞书文档上进行管理，包括 Bug 的提交、修复、验证、关闭等。

这里需要集成下飞书 MCP，如何集成在我另一篇文章[飞书文档MCP集成](/AI/飞书MCP.md)中讲解。

同时创建`.cursor/skills/feishu-bugs`文件夹，文件夹内创建一个`SKILL.md`文件，文件内容大致如下：

```md
# 飞书问题表改 Bug
## 何时做
## 禁止
## 流程
```

因为bug表格内容太多，所以加了一项**默认拉取当前正在改的活动**。

### 代码提交和部署

项目通过`Husky`配置`Git hooks`，在提交过程中执行代码检查和格式化：`ESLint`检查代码问题，`Prettier`统一代码格式，`commitlint`校验提交信息是否符合约定。

代码推送到`阿里云 Code`后，符合触发条件的`Webhook`事件会通知`Jenkins`执行构建和部署。部署成功后，再通过钉钉群消息通知相关人员。

这样，前面的 Agent 开发流程就接入了项目已有的代码检查和发布流程。

## 总结

以上就是巨鲸工作流的设计思路和实现方式。

整理这套工作流时，我主要做了三件事：

1. 接通信息来源：通过 MCP 和脚本，让 Agent 能够读取原型、设计稿、接口文档和飞书中的业务资料。
2. 固定重复操作：把经常使用的处理步骤和约定写进 Skill、Rule，减少每次对话中重复说明的内容。
3. 保存执行结果：将原型说明、接口文档、审核报告等资料保留在项目中，作为后续任务的依据。

从设计上看，每一个环节清晰明了，每一个环节都有对应的 Skill 和 Rule 来实现，有对应的文档来记录。这一点类似于`OpenSpec`，不过我去掉强制步骤，可以根据实际情况选择性执行。

我仍然保留了人工确认：需求是否理解正确、页面是否符合设计、Bug 是否真正解决，都需要结合实际业务判断。Agent 负责执行可以明确描述的任务，已有的代码检查和发布流程则继续提供约束。

后续如果保持稳定运行，可以考虑搭建为自动化流水线。

本文只介绍了工作流相关，实战中还有`my-lanhu-mcp.mdc`做本地缓存和 URL 补全，`Vue3.mdc`最佳实践，以及对应的地图导航`docs`文件。
