# AI Coding：内置浏览器与 Playwright 自测怎么选

在前面的[框架选型](/AI/AI-Coding如何选择自测框架.md)与[H5 实战](/AI/AI-Coding实战为Vue-H5接入Playwright自测.md)中，我们讨论了如何让 AI 编写并执行 Playwright 用例。

但 Codex 已经能直接操作浏览器：打开页面、点击按钮、填写表单、观察结果。既然如此，是否还需要给项目安装 Playwright、维护 spec？

我的建议是：开发中用浏览器探索，关键业务用 spec 回归。两种方式承担不同任务，可以由同一个 AI Agent 协调执行。

## 1. 比较的是两种执行方式

这里的区别在于，谁来决定测试步骤，以及验收标准保存在哪里。

| 方式 | 如何执行 | 验收标准 |
| --- | --- | --- |
| AI 直接操作内置浏览器 | 根据任务描述与页面当前状态，选择下一步操作 | 来自需求、检查清单和 AI 的现场判断 |
| Playwright spec + Skill | Skill 指导 AI 选择和执行用例，测试运行器执行固定步骤 | 保存在测试代码中的显式断言 |

Codex 同样可以编写和执行 Playwright spec，所以不必在 Codex 与 Playwright 之间二选一。

按[官方 Browser 文档](https://learn.chatgpt.com/docs/browser)，桌面内置浏览器支持页面操作与渲染结果检查；网络、控制台等深入诊断依赖可用的 Developer mode 和相应访问设置。具体能力应以当前客户端提供的工具为准。

下面的比较聚焦于自测方法，不假设所有浏览器会话都具有相同的调试能力。

## 2. 两种方式的优劣

| 维度 | 内置浏览器探索 | Playwright spec 回归 |
| --- | --- | --- |
| 开始成本 | 较低，提供页面和检查目标即可开始 | 需要安装依赖、配置运行环境、编写用例 |
| 探索能力 | 能根据页面情况继续尝试，发现未预设的问题 | 主要验证已经写入测试的行为 |
| 页面变化 | 可以重新理解布局并调整操作 | 定位器、步骤或预期可能需要维护 |
| 验收标准 | 需要任务描述和检查清单约束 | 断言明确，可以随代码审查与版本管理 |
| 重复性 | 每次路径、检查深度可能不同 | 相同条件下更容易复现与比较 |
| 接口检查 | 可结合当前可用的浏览器诊断能力 | 便于精确检查参数、响应、调用次数与时序 |
| 异常场景 | 依赖现场数据或额外构造状态 | 可以通过 Mock 稳定构造错误、空数据等状态 |
| 视觉检查 | 适合观察溢出、遮挡、多语言布局等问题 | 普通功能断言覆盖有限，需要额外的视觉检查方案 |
| 批量执行 | 更适合范围明确的交互式任务 | 适合批量回归、CI 和结构化报告 |
| 维护成本 | 少维护脚本，但每轮探索仍需要 AI 参与 | 有脚本维护成本，固定流程重复运行通常更经济 |

这些是使用方式带来的倾向，不能直接理解成稳定性或成本保证。AI 也可以严格执行清单，spec 也可能因定位器、异步等待或数据争用而不稳定。

## 3. 内置浏览器擅长发现什么

对于刚完成、还在频繁调整的活动页，先让 AI 实际使用页面很有价值。

以首充活动为例，可以让它检查：

- 手机尺寸下，奖励名称是否溢出、按钮是否被遮挡。
- 阿拉伯语方向下，金额、进度和弹窗布局是否合理。
- 规则弹窗能否打开与关闭，关闭后是否保留页面位置。
- 切换页面状态后，按钮文案和展示结果是否矛盾。

这类问题不一定已经写进需求清单。AI 可以结合视觉和操作反馈继续探索，定位不合理的表现。

但“请自测一下”仍然过于宽泛。AI 可能只打开首页、点击一个弹窗就结束；即使这一轮覆盖比较完整，下一轮也未必走相同路径。

更好的任务描述要包含页面、状态、操作、预期与范围。例如：

```text
检查首充活动的移动端展示与规则弹窗。
分别检查中文、英文和阿拉伯语，关注文字溢出、遮挡和方向。
打开并关闭规则弹窗，确认可以正常返回页面。
本次不领取奖励、不充值。
逐项报告已验证、失败和因数据条件无法验证的项目。
```

如果任务需要截图，应按项目规则明确要求。浏览器探索的结果也需要有具体观察依据，例如哪个语言、哪个区域、什么状态出现问题，方便复现。

## 4. Playwright 擅长固定什么

当某条业务规则已经明确，而且后续修改需要持续保证它成立，就适合写成 spec。

例如首充页面的三个任务状态：

```text
任务未完成 → 显示“未完成”
任务已完成但未领取 → 显示“领取”
任务已领取 → 显示“已领取”
```

用 Mock 准备这三类数据，再断言页面结果，每次修改后都可以重复验证，不必等待真实账号恰好处于对应状态。

真实接口流程也可以固定下来：打开页面、捕获首页响应、验证业务码、核对金额与状态。在有专用测试数据时，还可以验证领取后的重新查询结果。

不过，测试只能证明断言覆盖的内容。仅检查“按钮存在”，无法保证它提交了正确的任务 ID；仅检查“HTTP 200”，也不能保证业务执行成功。

视觉问题同样可能漏掉：即使布局明显拥挤，元素仍可被定位，功能断言也可能全部通过。需要视觉回归时，可以额外设计截图对比，但要维护基准，并处理字体、动画和动态内容造成的差异。

## 5. 真实接口与 Mock 是另一条选择轴

是否使用内置浏览器，与是否连接真实后端，没有必然关系。

| 验证方式 | 数据来源 | 适合验证 |
| --- | --- | --- |
| 内置浏览器探索 | 真实测试后端 | 实际账号下的页面与操作结果 |
| 内置浏览器探索 | 本地测试数据或已配置的 Mock 服务 | 特殊状态下的展示与交互 |
| Playwright spec | 真实测试后端 | 固定业务链路、协议兼容性与结果一致性 |
| Playwright spec | 测试代码拦截请求并返回 Mock | 可重复的边界场景与前端状态处理 |

要注意，给内置浏览器提供 Mock 数据，需要页面、服务或其他测试设施的支持，不能仅凭一句“模拟失败”就认为请求已经被正确拦截。

两种方式都需要验证预期。如果只看到页面正常加载，就宣布接口正确，结论仍然缺少依据。真实数据是否算错，需要已知的测试前提与预期结果；数据能够被展示，只能证明其中一部分链路成立。

## 6. Skill 能统一流程，spec 能固定断言

Skill 可以约定 AI 的执行要求，例如：

- 先读取需求、页面和接口说明。
- 明确本次是探索、回归，还是两者都做。
- 使用项目默认测试环境，按约定取得测试身份。
- 分别汇报真实接口、Mock 和未执行的场景。
- 失败时保留证据，不用跳过或放宽断言掩盖错误。

但 Skill 中写着“检查保存正确”，并不会自动得到一条可重复执行的测试。仍然需要进一步明确：提交了什么、响应如何判定成功、重新查询哪个记录、预期字段是什么。

这些条件进入 spec 后，才有了可以独立执行与审查的检查。

一个 Skill 可以同时管理两种路径：新页面先执行探索检查；已有用例先运行回归；发现重要缺陷后，将对应场景补充到 spec。具体检查方式仍应受当前任务范围和项目规则约束。

## 7. H5 活动项目如何组合

活动相对独立、开发周期较短时，不必一开始把所有交互都脚本化。可以按风险和复用价值逐步投入。

| 阶段 | 推荐做法 | 主要产出 |
| --- | --- | --- |
| 页面初版 | 内置浏览器探索主要流程和展示 | 问题记录、复现条件、待验证项 |
| 接口对接 | 使用测试账号检查真实请求与页面结果 | 联调结论、协议或数据问题 |
| 交付前 | 固定少量关键 spec，补充必要 Mock 场景 | 可重复执行的验收用例 |
| 修改后 | 运行受影响的 spec，再做针对性的浏览检查 | 回归结果与新发现的问题 |
| Bug 修复 | 将有价值的复现步骤固化为用例 | 防止同类问题再次出现的断言 |

优先维护那些失败影响较大、规则明确或多次出现问题的链路，例如鉴权参数、金额转换、按钮状态、重复点击和操作后的数据刷新。

变化很快的一次性展示区域，可以先用探索检查。公共鉴权、语言方向和请求封装等长期复用的能力，则值得维护更稳定的自动化测试。

两种浏览器方式都不能完整替代 App 真机验证。原生桥、充值跳转、WebView 生命周期以及设备上的动画兼容性，需要在实际宿主中补验。

## 8. 自测结论如何写

混合使用两种方式后，报告应把范围分别说明。以下仅为格式示例，不代表已执行测试：

```text
浏览器探索：
- 中文、英文规则弹窗可以打开并关闭。
- 阿拉伯语某处文案溢出，已记录复现位置。

Playwright Mock：
- 三种任务状态断言通过。

真实接口联调：
- 首页业务响应与金额展示一致。
- 领取链路未执行，本次仅验证读取。

未覆盖：
- App 内的充值跳转与原生桥。
```

“AI 看过页面”和“所有自动化用例通过”各自都只有明确的覆盖范围。把检查清单、断言结果与未覆盖项一起保存，下一次修改时才知道哪些结论可以复用，哪些还需要重新验证。
