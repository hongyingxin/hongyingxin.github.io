# Coding Agent 后台迁移复盘

最近完成了一次后台迁移：把过渡后台的页面迁到全球服后台，最终涉及47个业务页面。我使用 Coding Agent 参与代码分析、页面迁移、接口适配、自测和文档整理，也在过程中不断调整与 AI 的协作方式。

回头看，这次值得记录的地方，是我怎样拆任务、给上下文、检查结果，以及在 AI 的实现偏离预期时，把它拉回来。

## 1. 先让 Agent 理解项目和迁移范围

项目里同时存在旧版区域后台、过渡后台和全球服后台，部分页面名称相同，实现和维护状态却不同。迁移前，我先和 Agent 一起梳理项目关系、页面范围、来源分支和目标分支。

这些信息会直接影响迁移结果。来源版本选错了，可能把尚未纳入范围的新功能一起迁过来；只看页面文件，又可能遗漏 API、路由、权限、国际化和公共组件。

因此，我逐渐把“迁移这个页面”补充成更明确的任务：从哪个版本迁、迁到哪里、需要保留哪些行为、允许增加哪些差异，以及完成后怎么验证。项目里的 `AGENTS.md`、迁移 Skill 和业务文档，也成为 Agent 开始工作前需要读取的上下文。

## 2. 多窗口与多智能体协作，也需要划定边界

页面多起来后，串行推进开始显得低效。我之前就问过 Agent：

> 我想知道如何使用多窗口，因为需求分散，我不想等你做完一点再继续，而是一起改。

当时讨论了两种组织方式：独立需求开新窗口，方便我分别跟进；范围明确的子任务交给子智能体，由主智能体协调和汇总。后续迁移中，我按页面拆分任务，分批启动多个窗口，并统一跟踪进度。

但并行之后，新的问题也出现了。

这次不少窗口共用工作目录和功能分支。页面目录虽然不同，却可能同时修改同一个路由文件、API 导出文件或公共文档。因此，共享文件需要明确由哪个窗口维护，各任务也要知道自己负责的范围。

还有一次，多个窗口同时操作浏览器上传文件，发生了系统文件选择框争用。后来需要错开上传；后续集中回归时，我也要求使用同一个内置浏览器标签，逐页验证。开发任务能并行，浏览器操作仍然要考虑共享资源。

另一个更明显的问题，是**新窗口没有自动获得之前的排错经验**。

前面已经遇到过区域代理、参数传递等问题，后面新开的窗口仍可能重复排查，甚至过早判断需要后端处理。我又让主窗口把已有结论、排查顺序和成功案例同步过去，减少每个任务重新摸索的成本。

这让我意识到，拆分任务时，除了分配页面，还要传递已经确认的事实。

## 3. 多大区适配，需要逐个确认接口依据

迁移中的多大区适配就是一个典型例子。页面增加了大区选择，并不代表接口适配完成。有的接口走中心服务，有的需要区域代理，还涉及大区请求头、查询参数和保存时的区域上下文。

部分页面曾出现中心接口返回 `9001` 或 `404` 的情况。后来对照已有实现、后端文档和真实请求，修正代理或参数后才正常工作。这里也不能形成“报这个错误就统一改代理”的简单规则，每个接口仍然要有依据。

我把这些经验补进迁移规则，要求 Agent 连同列表、详情、下拉选项、保存和状态操作一起核对，避免只修好了列表，弹窗里仍然使用另一套调用方式。

## 4. 一次影响43个页面的公共封装调整

代码审查中，最让我印象深刻的是一次公共封装调整。

迁移过程中，Agent 新增了大区查询 Hook，逐渐被43个页面使用。它集中处理切区、查询和操作状态，看起来有复用价值，但也增加了一层调用关系和维护成本。

我当时反复追问：

> 原来的写法不行吗，才要换成这套？

接着让 Agent 对比迁移前后的实现，检查已有公共组件能提供什么、新封装额外做了什么，以及移除后会影响哪些页面。

最后，我决定去掉这层封装，让页面回到已有的通用表格实现，再针对变更做回归。这段返工让我更关注 AI 的架构选择：生成代码是否符合项目已有习惯，新增抽象是否值得长期维护，都需要有人判断。

## 5. 从 Mock 自动化测试，到真实接口验证

测试方式也经历了一次调整。

前期常用语言管理页面使用了 Playwright E2E＋Mock。它确实发现过问题：编辑后再打开新增表单，控件仍然处于禁用状态。修复后重新运行，用例通过，后续又补充了区域适配相关场景。

但看到测试通过后，我继续问：

> 全部跑 Mock 数据而没有调用接口吗？

这个问题让我重新区分了测试结果的含义。真实浏览器执行了操作，数据仍然可能来自 Mock；前端按预期发送请求，也不代表真实后端能够处理。

后续迁移中，我把验证重点转向内置浏览器：打开来源后台和目标后台，对照页面行为，操作真实测试接口，检查提交结果，并在保存后重新查询。

这次调整与当时使用的 Mock 方案有关。Playwright 同样可以连接真实后端，只是我们前期的用例主要验证前端行为，不能替代真实接口联调。

对 Agent 的自测要求，也逐渐从“测一下”变得具体：

- 新增后能否按记录重新查到数据。
- 编辑保存后，重新打开是否显示修改后的值。
- 发布、撤销后，状态是否真的变化。
- 切换大区失败时，旧数据和操作入口是否得到正确处理。

这些步骤让“测试通过”有了可以核对的依据。

## 6. 明确每一种检查能证明什么

ESLint 和 TypeScript 检查也需要分别看待。有些修改通过了 ESLint，完整类型检查仍然报错。我要求 Agent 按文件和诊断内容对比基线，判断问题与本次迁移的关系，再决定修复范围。

最终仍有类型问题被明确记录并暂缓处理，部分写入、区域和权限场景也按约定保留了未测说明。因此，这次完成迁移，指的是完成了约定范围内的交付；文章里也不能把它描述成所有检查、所有场景都已通过。

随着任务推进，迁移规则、接口排查顺序、测试记录和交接文档越来越重要。

它们让新窗口能接着已有结论工作，也让我能看清一个页面究竟处于什么状态：代码已接入、接口已确认、真实操作已验证，还是仍有明确的限制。后续修改公共组件时，也能据此判断哪些历史测试结论需要重新验证。

## 7. 我会带到下一次任务里的经验

最终，47个页面完成迁移并合入测试分支。这个过程中，我逐渐把精力放到了任务边界、上下文组织、代码审查和验收判断上，Agent 则承担了大量检索、实现、检查和修复工作。

下一次做类似任务，我会更早把一个代表性页面的迁移和验证流程跑完整，确认任务模板与共享文件边界后，再扩大并行范围；同时把重复出现的问题沉淀为 Skill，把值得长期回归的场景固定为测试用例，让下一轮协作能直接接着这次的经验开始。
